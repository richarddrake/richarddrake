## 1. 产品概述

测试用例智能生成系统是一套面向测试设计、接口测试执行与 Web UI 自动化执行的 AI 平台。系统支持用户上传思维导图、流程图、界面截图、表格、文档和外部链接等多种材料，并结合用户输入的测试要求、业务背景和上下文信息，自动生成结构化测试用例，支持页面展示、Excel 导出、历史记录、报告汇总、缺陷跟踪、接口执行和 Playwright UI 自动化执行。

当前版本已经从单一的“AI 生成用例工具”演进为具备以下四类能力的综合平台：

1. AI 测试设计能力
2. 接口与 Web UI 自动化执行能力
3. 测试资源保存与历史查询能力
4. 报告汇总与失败项跟踪能力
5. 登录认证与基础权限管理能力

## 2. 建设背景

在传统测试工作中，测试人员经常面临以下问题：

1. 需求材料来源分散，既有图片、流程图，也有 PRD、接口文档和表格，整理成本高。
2. 测试用例编写依赖人工分析，效率受个人经验影响较大。
3. 接口文档与实际测试执行之间存在断层，生成出来的用例不一定能直接落地执行。
4. 用例、执行结果和历史记录分散在多个工具中，难以统一保存、查询和复用。

本系统的目标就是把“输入材料整理、测试设计、接口 / UI 执行、结果汇总、问题跟踪”串成一条统一链路。

## 3. 产品定位

当前产品可定位为：

**AI 测试设计、接口测试执行与 Web UI 自动化执行平台（初版）**

它不是只负责生成测试点的轻量助手，而是一套可完成“多源输入 -> AI 生成 -> 质量分析 -> 接口 / UI 执行 -> 报告汇总 -> 缺陷跟踪 -> 历史查询”的测试工作平台。

## 4. 目标用户

- 希望快速基于 PRD、页面稿、流程图生成测试用例
- 希望将接口测试设计与执行统一在一个平台中完成
- 希望保存测试资源并减少重复劳动

### 4.2 测试负责人 / QA Lead

- 希望提升团队测试设计效率
- 希望评估测试覆盖情况和用例质量
- 希望形成可复盘、可追踪的测试输出

### 4.3 研发 / 产品协作人员

- 希望快速查看测试重点和覆盖范围
- 希望把接口契约快速转成可执行测试
- 希望利用 AI 降低前期测试设计沟通成本

## 5. 当前版本核心价值

### 5.1 多源输入统一处理

支持图片、表格、文档、文本和链接等多种输入来源，能够把分散材料统一纳入测试设计上下文。

### 5.2 自动生成结构化测试用例

系统可以根据输入材料自动生成标题、前置条件、测试步骤、预期结果、优先级和覆盖标签等结构化用例内容。

### 5.3 支持接口测试和 Web UI 自动化执行

生成结果不只停留在“文档层面”，而是支持对接口类用例进行请求发送、断言校验、变量提取、链路串联和并发执行；同时新增 Playwright UI 自动化基础执行，用于验证页面跳转、表单操作、页面断言和失败证据采集。

### 5.4 支持覆盖率与质量评估

系统会从需求、接口、字段、异常、边界、权限等维度分析覆盖情况，并对用例的可执行性与可验证性进行评分。

### 5.5 支持结果导出、历史保存与执行闭环

测试结果支持自动导出为 Excel，同时可写入 MySQL，形成生成历史、执行历史、报告汇总和结果回查能力。

### 5.6 已有可复现的测试验证结果

当前项目已经补充平台自测记录，不再只描述“能做什么”，也记录“实际测了什么、测得怎么样”。最近一次验证使用平台自身后端接口和 `docs/demo/openapi.json` 演示 Swagger 契约作为被测对象，覆盖了 Swagger 导入、用例生成、覆盖率分析、接口执行、数据库校验、轻量并发和 Excel 导出。

关键结果如下：

- Swagger 导入识别 3 个接口操作，生成 8 条接口测试用例。
- 生成用例自动化就绪 8/8，自动化就绪比例 100%。
- 用例质量平均分 97.6，接口覆盖率 100%，字段覆盖率 87.5%，异常场景覆盖率 50%。
- 接口执行器自测 4 个接口用例全部通过，31 个断言全部通过。
- 数据库只读校验 1 项，通过 1 项。
- 轻量并发验证 5 次请求全部通过，平均耗时 111.8 ms，P95 耗时 145 ms。
- Excel 导出文件 `generated/test_cases_evidence_20260623.xlsx`，包含 8 条生成用例。

验证过程中还发现过一次“旧测试预期与当前接口响应不一致”的断言失败：旧用例仍在检查英文服务名，当前接口实际返回中文服务名。修正断言后全部通过。这说明平台执行器不仅能展示通过结果，也能发现真实的断言漂移问题。

完整记录见：[`docs/TESTING_EVIDENCE.md`](TESTING_EVIDENCE.md)

### 5.7 外部业务系统实战验证

为避免验证对象只停留在平台自身接口，本项目已经接入小牛电商订单测试实战项目作为外部被测系统。该系统覆盖登录、鉴权、商品、购物车、订单、支付、取消和管理员重置等典型电商链路。

本轮沉淀了 3 份测试材料：

- `docs/demo/xiaoniu_ecommerce_prd.md`：需求分析和测试范围。
- `docs/demo/xiaoniu_ecommerce_test_cases.md`：45 条接口测试用例。
- `docs/demo/xiaoniu_ecommerce_api_suite.json`：可直接执行的接口用例集。

实际执行结果：

- 执行接口步骤 45 个，通过 40 个，失败 5 个，步骤通过率 88.89%。
- 执行断言 148 个，通过 138 个，失败 10 个，断言通过率 93.24%。
- 发现数量为 0 加入购物车、库存为 0 商品可加入购物车、超库存数量可加入购物车、已支付订单可重复支付等问题。
- 执行过程中同步修复平台接口执行器的变量替换问题，使断言期望值支持 `{{variable}}`。

这说明平台已经可以支撑真实业务系统的接口回归测试，而不是只做演示级自测。

### 5.9 Docker 一键演示环境

本次补充 Docker Compose 编排能力，将 Vue 前端、FastAPI 后端和 MySQL 数据库组成可复现的本地演示环境。前端镜像使用 Nginx 托管构建产物，并将 `/api`、`/docs` 和 `/openapi.json` 代理到后端容器；后端镜像负责运行 FastAPI 服务并连接 Compose 内部 MySQL；MySQL 容器通过初始化脚本准备演示数据库。

该能力主要用于降低项目演示和测试环境搭建成本。使用者安装 Docker Desktop 后，可以通过 `scripts/docker-start.cmd` 或 `docker compose up --build` 一键启动完整平台，通过 `scripts/docker-stop.cmd` 停止环境。

### 5.10 Redis 高并发支撑能力

当前版本在 FastAPI + Vue + MySQL 架构中引入 Redis。Redis 不替代 MySQL，而是承担缓存、后台任务队列、任务状态、限流和分布式锁职责。平台对历史记录、接口执行历史和 UI 执行历史增加短 TTL 缓存，降低报告中心和历史列表的重复查询压力。

同时，平台新增 Redis 后台任务队列，把单接口执行、接口用例集、并发执行和 Playwright UI 自动化从“同步等待结果”扩展为“提交任务、后台执行、前端任务中心查看进度”。任务提交会进行用户级限流，并使用 Redis 锁降低重复点击造成的重复执行风险。该能力让平台更接近真实测试执行中心的调度模式。

### 5.11 登录系统与用户权限管理

当前版本新增账号密码登录系统，平台打开后先进入登录页，登录成功后才能访问用例生成、Swagger 导入、接口执行、UI 自动化、报告中心、缺陷跟踪和历史记录等业务功能。后端使用 HttpOnly Cookie 保存登录态，密码以加盐哈希形式存储，并提供登录审计记录。

系统启动时会根据环境变量自动初始化默认管理员账号。管理员可以在前端用户管理模块创建 `admin` 或 `tester` 用户，并启用或禁用账号；普通测试人员可以使用平台测试功能，但不能进入用户管理。该能力让平台从单人演示工具进一步接近团队内部系统的使用形态。

### 5.12 GitHub Actions CI/CD

当前版本补充 GitHub Actions CI/CD 流程。代码推送到 `main` 分支或提交 pull request 时，CI 会自动执行后端 Python 编译检查、前端 Vue 构建、Docker Compose 配置校验，以及前后端 Docker 镜像构建检查。

在 `main` 分支 push 场景下，工作流还会使用 GitHub Token 登录 GitHub Container Registry，并将后端和前端镜像分别发布为 `latest` 与 `sha-xxxxxxx` 两类标签。若仓库配置了服务器 SSH secrets，CD 会继续上传生产 Compose 文件和部署脚本到服务器，拉取本次提交对应的镜像标签，并通过 `docker compose up -d` 完成自动更新。该能力用于在代码合并前发现语法错误、前端构建错误和容器化配置问题，并把“构建产物”推进到可部署运行环境。

## 6. 核心功能模块

## 6.1 多源材料输入

当前支持的输入类型包括：

- 图片：思维导图、流程图、界面截图
- 表格：Excel、CSV、TSV
- 文档：Word、PDF、Markdown、TXT、JSON、YAML、HTML、日志类文本
- 链接：飞书文档、PRD、接口文档、普通网页，其中飞书 docx、docs/doc 和 wiki 可在配置开放平台应用后读取正文
- 用户补充输入：测试要求、上下文背景、业务说明

该模块解决的是“测试设计前的材料收集与整理”问题。

## 6.2 AI 测试用例生成

系统可基于输入材料自动生成结构化测试用例，当前生成结果通常包括：

- 用例标题
- 需求追溯字段 requirement_id（如材料中可识别）
- 前置条件
- 测试步骤
- 预期结果
- 优先级
- 覆盖标签
- 测试数据建议
- 部分接口类用例的执行配置
- 部分页面类用例的 ui_test 执行配置
- 用例是否可执行、不可执行原因和补齐建议

系统支持流式输出，前端可边生成边展示，提升可感知性和等待体验。

## 6.3 用例展示与工作台

前端当前已经形成统一工作台，支持：

- 工作台录入
- 用例卡片视图
- 用例表格视图
- 用例生成结果查看
- 用例评审结论查看
- 报告中心查看
- 缺陷跟踪查看
- 历史记录查看
- 历史记录内下载 Excel

整体界面以科技风和集中工作台为主，便于连续操作。

当前右侧主内容区已经按测试流程顺序组织为：

1. 工作台
2. 用例生成
3. 用例评审
4. UI 自动化
5. Swagger 导入
6. 接口执行
7. 报告中心
8. 缺陷跟踪
9. 历史记录

本次对前端视觉密度和界面层级做了进一步优化，缩小了主标题、侧栏、模块卡片、表单控件、按钮、统计块和空状态区域的尺寸，并弱化大面积阴影与装饰渐变，让页面更接近测试平台日常使用场景下的紧凑工作台，而不是大字号、大卡片的展示型页面。

## 6.4 用例评审

用例评审模块用于把生成结果从“可展示”提升到“可进入评审会或执行前检查”的状态。当前支持：

- 按通过、需修改、阻塞给出整体评审结论
- 汇总总用例、通过数、需修改数、阻塞数和质量均分
- 从需求追溯、步骤完整、预期可验证、执行就绪和评审通过五个维度形成检查清单
- 自动识别重复标题、缺少需求追溯、步骤或预期不完整、自动化执行信息未补齐等问题
- 为每条用例给出评审状态、问题标签和修改建议

这个模块适合在 AI 生成或 Swagger 导入之后、接口执行之前，快速判断哪些用例可以进入执行，哪些需要先补充。

## 6.5 Swagger / OpenAPI 导入

系统支持导入 OpenAPI / Swagger 的 JSON 或 YAML 文档，自动生成接口测试用例。

当前重点覆盖的测试场景包括：

- 正向场景
- 缺参场景
- 非法参数场景
- 边界值场景
- 权限校验场景
- 幂等性相关场景

该能力适合“已有接口契约，想快速落测试”的团队。

## 6.6 接口测试执行

系统已具备基础到中等强度的接口执行能力，支持：

- 单接口执行
- 用例集顺序执行，单个用例集最多支持 500 个步骤
- 并发执行
- 重复执行
- 失败中断
- 变量提取与接口串联

支持的方法包括：

- GET
- POST
- PUT
- PATCH
- DELETE
- HEAD
- OPTIONS

支持的请求体格式包括：

- raw
- json
- form
- multipart

## 6.7 Web UI 自动化执行

系统新增 Playwright UI 自动化基础执行能力，用于把页面级测试从“用例设计”推进到“浏览器执行验证”。

当前第一版重点支持：

- 受控步骤 DSL，不执行用户粘贴的任意脚本
- Chromium / Firefox / WebKit 浏览器选择，默认 headless 执行
- 页面基础地址、变量 JSON、步骤 JSON 和视口配置
- 页面动作：打开页面、点击、填写、输入、按键、选择、勾选、等待元素、固定等待和截图
- 页面断言：元素可见 / 隐藏、文本可见、URL 包含 / 等于、标题包含、元素文本包含
- 失败截图和 Playwright trace 证据
- 控制台消息和网络失败摘要
- UI 执行历史保存，并纳入报告中心和缺陷跟踪

该模块当前适合验证登录、搜索、表单提交、页面跳转、状态提示、权限可见性等稳定页面流程。验证码、短信、人脸识别等强人工环节仍需要测试环境旁路或人工处理。

## 6.8 报告中心

报告中心用于把接口执行和 UI 自动化执行结果从“单条执行记录”提升为“可汇总查看的测试报告”，当前支持：

- 汇总最近执行次数、通过数、失败数和通过率
- 展示最近接口和 UI 自动化运行记录
- 展示当前覆盖风险数量和概览提示
- 结合用例质量评分、执行状态形成阶段性测试视图
- 支持导出 Markdown / HTML 测试报告，便于存档和分享
- HTML 报告已经覆盖报告概览、测试环境、测试范围、执行统计、覆盖率、质量分析、失败分析、缺陷跟踪、慢执行、数据库校验、风险提示、测试结论和执行明细

这个模块适合在一次测试执行后快速给出“本轮执行情况怎么样”的答案。

## 6.9 缺陷跟踪

缺陷跟踪模块用于对失败项进行持续管理，当前支持：

- 自动同步接口执行和 UI 自动化失败项
- 区分待处理、处理中、已解决三种状态
- 维护优先级、负责人和跟踪备注
- 为失败项提供建议动作，方便继续定位问题
- 自动合并相同失败，统计重复出现次数
- 从缺陷记录回看最近一次执行详情和失败证据

这个模块让平台从“发现失败”走向“持续跟踪失败项”。

## 6.10 断言与数据库校验

当前支持的断言与校验能力包括：

- 状态码断言
- 响应内容断言
- Header 断言
- JSONPath 断言
- 正则断言
- 存在性断言
- 大小比较
- JSON Schema 校验
- 响应时间断言
- MySQL 只读 SELECT 校验
- 页面可见性、URL、标题和文本断言

这部分能力使平台具备“从设计结果走向实际执行验证”的基础条件。

## 6.11 覆盖率与质量评分

系统当前会从以下维度分析覆盖情况：

- 需求
- 接口
- 字段
- 异常
- 权限
- 边界
- 数据一致性
- 性能
- 安全

同时会对生成用例进行质量评分，关注：

- 步骤可执行性
- 预期可验证性
- 测试数据充分性
- 覆盖标签完整性
- 自动化就绪度
- 重复度

当前前端已经补充：

- 每个维度的扣分原因
- 不可执行原因
- 未覆盖项和补充建议
- 质量建议与风险提示

## 6.12 失败分析与历史查询

在接口执行或 UI 自动化执行失败后，系统可对失败原因进行分类分析，例如：

- 环境问题
- 鉴权问题
- 参数问题
- 断言问题
- 契约变更
- 后端缺陷
- 数据一致性问题
- UI 定位器问题
- UI 超时
- 页面访问或页面网络问题

当前失败分析结果除结论外，还会补充：

- 失败证据摘要
- 失败分类置信度
- 下一步排查建议
- 是否建议纳入缺陷跟踪
- 是否建议更新测试用例
- Markdown / JSON 分析报告下载

如果启用 MySQL，系统还能保存：

- 生成会话
- 输入摘要
- 材料摘要
- 用例明细
- Excel 下载地址
- 接口执行历史
- UI 自动化执行历史
- 响应摘要
- 断言结果
- 接口失败分析结论、证据和排查建议
- 变量提取结果
- 执行耗时

### 6.13.2 当前系统边界

当前版本需要明确以下边界：

1. 私有飞书链接需要先配置飞书开放平台应用并授予文档 / Wiki 读取权限；未配置、无权限或非文档类链接仍更适合上传导出文件或粘贴关键内容。语雀、Confluence 等私有链接当前仍按普通链接线索处理。
2. AI 生成结果仍建议人工确认，尤其是接口地址、鉴权方式、页面地址、稳定定位器、测试数据和数据库断言。
3. 当前 Playwright UI 自动化是基础版，支持受控步骤执行、截图和 trace，但还不是完整的可视化编排器、录制平台或 CI 回归用例管理系统。
4. 当前数据库校验只支持 MySQL 只读 SELECT。
5. 当前报告中心已经支持基础汇总和 Markdown 导出，但还不是完整的 PDF 测试报告系统。
6. 当前缺陷跟踪是内部失败项管理，不等同于 Jira、禅道等外部系统的完整联动。
7. Swagger 导入已覆盖常见 schema，但面对非常复杂的跨文件契约、定制鉴权和项目级规则时仍建议人工复核。

## 7. 用户使用流程

### 7.1 AI 生成主流程

1. 用户进入工作台
2. 上传图片、文档、表格或粘贴外部链接
3. 输入测试要求和上下文背景
4. 发起 AI 生成
5. 前端实时展示生成中的测试用例
6. 查看用例内容、覆盖率和质量评分
7. 进入用例评审，处理阻塞项和需修改项
8. 下载 Excel
9. 保存历史记录

### 7.2 Swagger 导入流程

1. 用户进入 Swagger 导入模块
2. 粘贴文档内容或填写文档 URL
3. 系统解析接口契约
4. 自动生成接口测试用例
5. 展示覆盖率和生成结果
6. 支持导出和历史查询

### 7.3 接口执行流程

1. 用户进入接口执行模块
2. 手工填写接口配置或使用已生成用例
3. 配置断言、变量提取和数据库校验
4. 执行单接口或用例集
5. 查看执行结果与失败分析
6. 保存执行历史

### 7.4 UI 自动化执行流程

1. 用户进入 UI 自动化模块
2. 填写页面基础地址、浏览器、视口和变量
3. 配置 Playwright 受控步骤和页面断言
4. 执行 UI 用例
5. 查看步骤结果、失败截图、trace、控制台消息和网络失败摘要
6. 将失败项同步到缺陷跟踪，并进入报告中心汇总

### 7.5 报告与缺陷跟踪流程

1. 用户进入报告中心查看最近执行汇总
2. 按通过率、失败数和覆盖风险判断本轮测试结果
3. 将失败项同步到缺陷跟踪模块
4. 为失败项补充优先级、负责人和备注
5. 跟踪状态变化，直到问题关闭

### 7.6 典型使用案例

案例 1：上传 PRD + 页面截图，生成登录模块测试用例

1. 上传登录模块 PRD
2. 上传登录页面截图
3. 填写测试重点：账号密码、验证码、账号锁定、忘记密码
4. 生成测试用例
5. 查看执行就绪状态、覆盖率和质量建议
6. 导出 Excel

案例 2：导入 Swagger，生成并执行接口测试用例

1. 输入 OpenAPI JSON 地址
2. 系统解析接口契约
3. 生成正向、异常、边界接口测试用例
4. 查看哪些用例可直接执行，哪些仍需补齐
5. 进入用例评审，确认接口用例是否具备执行条件
6. 执行接口用例
7. 查看断言结果、失败证据和报告中心汇总

案例 3：接口执行失败后生成报告并同步缺陷

1. 执行接口用例集
2. 部分接口失败
3. AI 分析失败原因并展示证据链
4. 生成测试报告
5. 同步失败项到缺陷跟踪
6. 负责人处理缺陷后重新验证

案例 4：执行登录页面 UI 自动化并保存失败证据

1. 进入 UI 自动化模块
2. 配置测试环境页面地址、账号变量和登录步骤
3. 使用 role、label、placeholder 或 text 定位页面元素
4. 执行 Playwright UI 用例
5. 如果失败，查看失败截图和 trace
6. 将失败项同步到缺陷跟踪，并在报告中心汇总本轮 UI 执行结果

## 11. 汇报结论

测试用例智能生成系统当前已经完成从“多源材料输入”到“AI 用例生成”再到“接口执行、UI 自动化基础执行、报告汇总、缺陷跟踪与历史查询”的基础平台化建设，具备了初版智能测试平台的雏形。

它的价值不再局限于帮助测试人员编写几条测试用例，而是在逐步形成一套覆盖测试设计、接口与页面执行验证、结果汇总和测试资源保存的统一工作平台。对于需要提升测试设计效率、提升接口与页面自动化落地能力和保存测试资源的团队来说，这套系统已经具备明确的试点和内部推广价值。
