## 1. 本轮验证对象

本轮使用平台自身作为被测系统，重点验证“接口契约导入 -> 用例生成 -> 接口执行 -> 数据库校验 -> Excel 输出 -> 指标汇总”这条链路。

## 2. 平台当前能测什么

当前平台已经可以覆盖以下测试内容：

- 接口功能测试：验证接口是否可达、状态码是否符合预期、响应体是否包含关键内容。
- 接口契约测试：基于 Swagger / OpenAPI 自动生成正向、缺参、非法参数、边界、稳定性等接口用例。
- 响应结构测试：支持 JSONPath 断言和 JSON Schema 校验。
- 数据库校验：支持执行只读 `SELECT`，用于验证接口执行后的数据库状态或数据一致性。
- 批量与串联测试：支持接口用例集顺序执行、变量提取和跨接口传递。
- 轻量并发测试：支持重复执行和并发执行，用于观察基础响应时间和稳定性。
- 覆盖率分析：按需求、接口、字段、异常、权限、边界、数据一致性、性能、安全等维度输出覆盖结果。
- 用例质量分析：评估步骤完整性、预期可验证性、测试数据、覆盖标签、自动化就绪度和重复度。
- 报告输出：支持在报告中心汇总执行结果，并导出 Markdown / HTML 报告。
- 测试资源保存：支持将生成结果保存为 Excel，启用 MySQL 后保存生成历史和执行历史。

## 5. 验证过程中发现的问题

第一次执行根接口健康检查时，测试用例仍然沿用了旧的英文响应预期，断言中要求响应体包含 `AI Test Case Generator API`。当前接口实际返回的是中文服务名和 `/docs` 路径，因此第一轮结果出现：

| 指标 | 结果 |
| --- | ---: |
| 执行用例数 | 4 |
| 通过用例数 | 3 |
| 失败用例数 | 1 |
| 断言总数 | 30 |
| 失败断言数 | 2 |

这个结果说明平台执行器能够发现“测试用例预期与实际接口响应不一致”的问题。修正断言预期后，第二轮正式执行结果为 4/4 用例通过、31/31 断言通过。

## 6. 阶段结论

本轮验证证明当前平台不是只能生成测试用例，而是已经可以形成可执行、可量化、可导出的测试链路：

- 可以从 Swagger / OpenAPI 契约自动生成接口测试用例。
- 可以输出覆盖率、自动化就绪比例和用例质量评分。
- 可以实际执行接口测试，并统计通过率、断言结果、响应时间和慢接口。
- 可以执行数据库只读校验，验证数据库连接和查询能力。
- 可以生成 Excel 测试用例文件，便于下载、归档和汇报。
- 可以发现断言预期不匹配这类真实测试问题。

当前验证对象仍以平台自身和 demo 契约为主。接入真实业务系统后，可以沿用同一套指标口径记录接口覆盖率、需求覆盖率、异常覆盖率、缺陷数、失败原因分类和测试结论。

## 7. 外部业务系统验证：小牛电商订单测试实战项目

> 验证时间：2026-06-24
> 被测系统：小牛电商订单测试实战项目
> 前端地址：`http://www.ceshixiaoniu.com/ecommerce-practice-app.html`
> 接口基础地址：`http://43.133.227.52/api`

为了补足“平台自测接口太少”的问题，本轮引入一个真实外部电商练习系统作为被测对象，围绕登录、鉴权、商品、购物车、订单、支付、取消和管理员重置等业务流程进行接口回归测试。

本轮新增测试材料：

| 文件 | 作用 |
| --- | --- |
| `docs/demo/xiaoniu_ecommerce_prd.md` | 小牛电商需求分析和测试范围 |
| `docs/demo/xiaoniu_ecommerce_test_cases.md` | 45 条接口测试用例清单 |
| `docs/demo/xiaoniu_ecommerce_api_suite.json` | 可由平台接口执行器直接运行的接口用例集 |

### 7.1 覆盖范围

本轮覆盖的问题包括：

- 登录鉴权：正确登录、错误密码、空账号、无 token、错误 token。
- 权限边界：普通用户不能执行管理员重置接口。
- 商品库存：商品列表字段、库存为 0、超库存数量。
- 购物车：查询、加入、删除、非法商品、非法数量、金额计算。
- 订单流程：创建订单、查询详情、支付、取消。
- 状态流转：重复支付、已支付取消、已取消支付。
- 异常场景：不存在订单、空购物车下单、删除不存在购物车商品。

### 7.2 平台能力调整

为了支持真实业务回归，本轮将接口用例集上限从 `30` 步扩容到 `500` 步；同时将前端“执行用例集”的默认策略调整为失败后继续执行，便于一次性收集完整失败清单。

执行过程中还发现并修复了平台接口执行器的一个问题：自定义断言中的 `expected` 字段原本没有执行 `{{variable}}` 变量替换，导致订单详情 ID 校验误失败。修复后，用例可以正确使用上一步提取的订单号进行断言。

### 7.4 失败项分析

| 用例 | 期望 | 实际 | 初步判断 |
| --- | --- | --- | --- |
| 数量为 0 加入购物车 | 返回 400 | 返回 200，并加入 1 件商品 | 参数校验缺陷 |
| 库存为 0 商品加入购物车 | 返回 400 | 返回 200，并加入购物车 | 库存边界缺陷 |
| 重复支付已支付订单 | 返回 400 | 返回 200，仍返回 success | 订单状态流转缺陷 |

### 7.5 阶段结论

这轮验证证明平台已经可以从“自测接口验证”升级到“真实业务系统接口回归”：

- 能够围绕登录、鉴权、商品、购物车、订单和权限边界设计完整接口用例。
- 能够通过变量提取串联 token、订单号等业务数据。
- 能够执行超过 30 步的完整业务用例集，并在失败后继续收集完整结果。
- 能够发现真实业务缺陷，例如参数校验缺失、库存边界缺失和订单重复支付问题。
- 能够把需求分析、测试用例和执行结果沉淀为项目文档，便于汇报和复盘。
